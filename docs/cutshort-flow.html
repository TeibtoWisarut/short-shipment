Cut Short Flow

แผนผังการทำงานทั้งหมดของเครื่องมือ Update Qty Cut Short — ตั้งแต่ process chain ของ Export, จุดแบ่ง Phase A/B, จนถึง write-set ที่แม่นยำของทั้ง 3 ระดับ short (Qty / Line / Container) กลับมาเปิดหน้านี้เพื่อทวนภาพรวมได้ทันทีโดยไม่ต้องไล่อ่าน Plan doc ใหม่ — ณ 2026-09-06 ผ่านการทดสอบจริงบน SB1 ครบทั้ง 3 ระดับ × 2 Phase แล้ว (พบและแก้บั๊กจริงรวม 8 จุดระหว่างทาง) ต่อมา 2026-09-07 เพิ่มการเขียน custrecord_item_info_qty_confirm ในเคส Qty-level (issue #1) — ทดสอบผ่านบน SB1 ด้วย SA จริง (SAE-PK-TH-DA-26070005) แล้ว deploy ขึ้น Production สำเร็จเมื่อ 2026-09-07 (เป็นการ go-live ครั้งแรกของ redesign ทั้งชุด เพราะ Prod ยังไม่เคยได้รับ deploy นี้มาก่อนเลย — ดู backup ก่อน deploy ที่ backups/prod_2026-09-07/)

01 — Domain

Process Chain ของ 1 Container

1 ตู้ container = 1 TO = 1 Wave เสมอ แต่ 1 ตู้มีได้หลาย item — เส้นทางนี้คือลำดับบังคับตั้งแต่เปิด PI จนถึง Gen IF จุดที่ระบบข้าม Phase A ไป Phase B คือ "Gen IF"

02 — Domain

03 — Logic

การตัดสินระดับ Short

ไม่มี checkbox "Line-level" แยกต่างหาก — ระบบดูแค่ 2 อย่าง: ค่าที่คำนวณได้ของ 1 Detail row (1 คู่ item×container) เท่ากับ 0 หรือไม่ และติ๊ก "Short whole container" ไว้หรือเปล่า

05 — Detail

รายละเอียดแต่ละเคส

คลิกเพื่อขยายแต่ละเคส — เนื้อหาเดียวกับตารางด้านบนแต่อธิบายเหตุผลประกอบ

1Qty-level — ลดบางส่วน ไม่ถึง 0

▸

เคส "ปกติ" ของเครื่องมือนี้ — ของยังส่งอยู่จริง แค่จำนวนคลาดจากแผน เช่น Gram Swing (น้ำหนักม้วนกระดาษจริงต่างจาก UOM เล็กน้อย)

เขียนอะไร

  • SA line: quantity, custcol_shortshipment_qty_old (ครั้งแรกที่เปลี่ยน), reason
  • Plan Load Detail: custrecord_item_info_short_qty_old (ใหม่), reason
  • Plan Load Detail: custrecord_item_info_qty_confirm = effectiveQty (Phase A = Wave Quantity, Phase B = Qty Shipped) — อัปเดต 2026-09-07 / issue #1, เดิมห้ามเขียนทับ ดูหมายเหตุความเสี่ยงด้านล่าง
  • TO line: quantity, custcol_shortshipment_qty_old, reason
  • Wave: reason (+ conv/NW/GW ถ้าติ๊ก "Do not Cal Conv" — ของเดิม ไม่เปลี่ยน)

ไม่แตะอะไร

  • isinactive บน Plan Load Detail
  • isclosed บน TO line
  • Heavy Container
ความเสี่ยงที่ยอมรับแล้ว: หลังจากนี้ custrecord_item_info_qty_confirm ของแถวที่เคยถูก Qty-level short จะไม่ใช่ยอดแผนดั้งเดิมอีกต่อไป — ถ้ามีคน Cancel Wave + Confirm ใหม่ (Regenerate) ในอนาคต ระบบจะได้ยอดที่ short ไปแล้วเป็นฐานแทนยอดแผนเดิม ยอดแผนดั้งเดิมจริงต้องไปดูที่ custrecord_item_info_short_qty_old แทน

2Line-level — 1 item ในตู้ = 0

▸

Item นี้ไม่ไปเลย แต่ item อื่นในตู้เดียวกันยังส่งได้ปกติ (ตู้มีได้หลาย item) — ไม่มี checkbox แยก เป็นผลจากค่า = 0 โดยไม่ได้ติ๊ก whole-container

เขียนอะไร (เพิ่มจาก Qty-level)

  • Plan Load Detail แถวนี้: isinactive = true
  • TO line นี้: isclosed = true — เฉพาะ Phase A และเฉพาะถ้ายังไม่ closed
  • Phase B: ไม่แตะ isclosed เลย (TO จบ lifecycle ผ่าน IF/IR ไปแล้ว)

ทดสอบแล้วบน SB1 sandbox

  • Close 1 line ของ TO หลายบรรทัด → Order Status ไล่ปกติ Pending Fulfillment → Pending Receipt → Closed ไม่เพี้ยน
  • TO line quantity=0 ถูก NetSuite บล็อกเสมอ ("must have a positive count") — Close คือทางเดียวที่ทำได้จริง
  • ไม่แตะ Heavy Container — ตู้จริงยังไปอยู่

3Container-level — ทั้งตู้ = 0

▸

ทุก item ในตู้นั้น short พร้อมกันหมด (เช่น อุบัติเหตุหน้าโรงงานก่อน Load) — ติ๊ก "Short whole container" แล้วระบบ auto-select ทุกแถวที่ container index เดียวกันให้

เขียนอะไร (= Line-level × ทุก item ในตู้)

  • ทุก Plan Load Detail row ที่ container index เดียวกัน: isinactive + reason + short_qty_old
  • ทุก TO line ของตู้นั้น: isclosed (Phase A) / ข้าม (Phase B) + qty_old + reason
  • Heavy Container 1 แถว (match ด้วย custrecord_hc_container_index + custrecord_hc_ref_sa คู่กัน — index อย่างเดียวไม่ unique ข้าม SA เจอจริงว่าซ้ำกัน 338 แถวทั้งระบบ): isinactive

Timing สำคัญ

  • Heavy Container ถูก set ครั้งเดียวหลังจากทุก item ในตู้สำเร็จครบ 100% เท่านั้น — ไม่ set แบบ per-item
  • ถ้ามี item ไหน fail ระหว่างทาง → ไม่ set Heavy Container เลย ปล่อยให้เห็น error แล้ว run ซ้ำ
  • ป้องกันเคส "ตู้ปิดไม่ครบ" ที่ Heavy Container บอกว่าตู้ไม่ไป ทั้งที่บาง item ยังไปจริง

Partial-failure & Retry

แก้ปัญหาเดิม: save_sa_body เคยใช้ยอดที่ "ควรจะเป็น" จาก payload ก่อนยิง AJAX ไม่ได้ปรับตามผลจริงของแต่ละ container

07 — Precision

SA 3 ตำแหน่ง vs TO/Wave conversion จริง

SA เปิดเป็น Qty ขาย แสดงสูงสุด 3 ตำแหน่งเสมอ — TO/Wave สร้างด้วย conversion จริงของ UOM แต่ละ item เพื่อตัดสต็อกแม่นยำ (อาจมี 3-5 ตำแหน่ง) ดังนั้น TO=9.8235 กับ SA=9.824 ในตัวอย่างเดียวกัน ถูกต้องแล้วโดยดีไซน์ ไม่ใช่บั๊ก

บั๊กที่เจอจริง (2026-09-06): ปัดเศษด้วย value.toFixed(3) ตรงๆ ไม่เสถียร — ค่าเดียวกันทางคณิตศาสตร์ให้ผลต่างกันได้ตามที่มาของตัวเลข เช่น 9.8235 (พิมพ์ตรงๆ) → toFixed(3) ได้ 9.823 (ปัดผิด) แต่ 10.4784 − 0.6549 (ผลลบ ค่าเท่ากัน) → toFixed(3) ได้ 9.824 (ถูก) — เกิดจาก floating-point ของ JavaScript เก็บทศนิยมไม่เป๊ะที่ตำแหน่งพอดี 5 แล้ว "ปัดสุ่ม" ไปคนละทาง ยืนยันจากผู้ใช้ว่าเจอเคสแบบนี้เป็นปกติ (conversion factor ลงตัวสวยๆ เจอ .xxx5 บ่อย) ไม่ใช่ edge case หายาก

แก้ด้วยฟังก์ชัน roundHalfUp(value, 3) (reparse ผ่าน exponential notation แทนการคูณ/ปัดตรงๆ) ใส่ทั้ง SL และ CS แทนที่ toFixed(3) ทุกจุดที่ใช้คำนวณยอดจริงไปเขียน SA — ทดสอบแล้วให้ผล 9.824 เสมอไม่ว่าที่มาของตัวเลขจะเป็นค่าดิบหรือผลลบ

บทเรียนรอบสอง (2026-09-06): แม้กรอง custrecord_hc_container_index + custrecord_hc_ref_sa คู่กันแล้ว ก็ยังเจอซ้ำได้อีก — ทุกครั้งที่ Plan Load ถูก Re-plan (ตัวเก่า Cancel ตัวใหม่ถูกสร้าง) ระบบภายนอกสร้าง Heavy Container แถวใหม่โดยไม่ inactivate แถวเก่า พบจริง 3 แถว active พร้อมกันสำหรับ container เดียวกัน ต่างกันแค่ custrecord_hc_ref_pl_no (คนละ Plan Load generation) แก้โดย resolve Plan Load header id ปัจจุบันจาก Plan Load Detail id ที่ Client ส่งมา (data-pl-id — id ที่เชื่อถือได้ ไม่ใช่ข้อความคอลัมน์ที่แสดง) แล้วกรองด้วย custrecord_hc_ref_pl_no เป็น filter ที่ 3 — verify แล้วว่ากระทบแค่แถวที่ตรงกับ Plan Load ปัจจุบันจริงเท่านั้น
บัคที่ 6 — Plan Load ที่ Cancelled แล้วยังเลือกได้: Saved search ของ grid Select Data ไม่มี filter isinactive ทำให้ Plan Load Detail ที่ถูก Re-plan/Cancel ไปแล้ว (isinactive=T) ยังโผล่มาให้ติ๊กเลือกซ้ำได้ — เจอจริงบน SA ตัวอย่างที่มี 30 แถว 20 แถวเป็นของเก่าที่ Cancel ไปแล้ว แก้โดยเพิ่ม filter isinactive = F ที่ตัว saved search โดยตรง
บัคที่ 8 — TO quantity ถูกเขียนผิดใน Phase B สำหรับ Qty-level: เดิมโค้ดเขียน TO line quantity ทุกครั้งที่ไม่ใช่ 0 (Qty-level) โดยไม่เช็ค Phase เลย ต่างจาก isclosed ที่เช็คถูกอยู่แล้ว — พอเทส Qty-level กับตู้ที่ Gen IF ไปแล้ว (Phase B) NetSuite reject ด้วย "Transfer orders can not be overfulfilled or overreceived" (TO ไม่เสียหายเพราะ validation ทำงานก่อน commit) แต่พบว่า Plan Load Detail ถูกเขียนบางส่วนไปแล้วทั้งที่ TO ยัง fail — แก้ 2 จุด: (1) เขียน quantity เฉพาะ !isZero && phaseAActive เท่านั้น (2) เพิ่ม flag กัน Plan Load Detail ไม่ให้เขียนถ้า TO section fail ไปก่อนแล้ว — verify ซ้ำผ่านทั้งคู่
การเปลี่ยนแปลง 9 — เปิดให้เขียน qty_confirm เฉพาะเคส Qty-level (2026-09-07, issue #1): เดิม custrecord_item_info_qty_confirm ห้ามเขียนทับเด็ดขาดทุกเคส (ดูบั๊กเดิมใน §02) ทีมตัดสินใจเปลี่ยนให้เคส Qty-level เขียนทับด้วย effectiveQty ได้ (Line-level/Container-level ยังคงห้ามแตะเหมือนเดิม) เพื่อให้ค่านี้สะท้อน wave qty ล่าสุดหลัง short — แลกกับความเสี่ยงที่ flow Cancel Wave + Confirm ใหม่ในอนาคตจะ regenerate จากยอดที่ short แล้วแทนยอดแผนเดิม (ยอมรับความเสี่ยงนี้แล้ว) ยอดแผนดั้งเดิมจริงยังกู้คืนได้จาก custrecord_item_info_short_qty_old ซึ่ง stamp ไว้ก่อนเขียนทับเสมอ
